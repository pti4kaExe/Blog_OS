BlogOS

Система для авторов Telegram-каналов и блогов. Три модуля: CommentRadar находит обсуждения и готовит ответы, Narrative Engine собирает посты из сырых заметок, AntiCringe проверяет текст на клише и отклонения от стиля автора.

1. Данные приложения

Что BlogOS должен хранить

Всего 13 сущностей. Я разложил их на четыре группы по тому, какая часть системы ими пользуется.

Автор и его стиль

  • Users — пользователь: Telegram ID, имя, дата регистрации.
  • AuthorProfiles — профиль автора: описание и настройки контента.
  • ToVProfiles — стиль автора: тональность, сленг, стоп-слова, любимые выражения.

Контент

  • Posts — опубликованные посты и их текст.
  • Drafts — черновики от автора или от Narrative Engine.
  • LintReports — результаты проверки AntiCringe.

CommentRadar

  • Sources — отслеживаемые Telegram-каналы и другие источники.
  • Comments — найденные в источниках комментарии.
  • GeneratedResponses — варианты ответов, которые готовит CommentRadar.

AI и качество

  • KnowledgeBase — факты и материалы авторской базы знаний.
  • Embeddings — векторы постов и материалов для RAG.
  • GenerationRuns — запуски AI: модель, токены, стоимость, статус.
  • GoldenDataset — эталонные тексты и разметка ошибок для Evals.

Что такое PK и FK

PK — номер записи, у каждой он свой. FK — номер записи из другой таблицы. Например, author_id в черновике показывает, какому автору он принадлежит. По таким полям таблицы и соединяются.

Зачем JSONB и vector

Замечания AntiCringe бывают разные, поэтому issues хранится как JSONB — гибкий список внутри одной ячейки. vector — числовое представление текста, по нему RAG ищет похожие посты.

Что я нашёл при сборке схемы и ещё нужно решить

  1. На общей диаграмме посты, черновики и источники подключены к users, а в ER-схеме — к author_id. На этой странице я взял вариант с author_id: он точнее, если у пользователя несколько каналов.
  2. База знаний на диаграмме ведёт в embeddings, но в embeddings есть только post_id. Нужно добавить поле, которое показывает, что вектор взят из базы знаний.
  3. Для knowledge_base, generation_runs и golden_dataset в ER-схеме полей не было. Здесь они собраны по описанию сущностей и требуют подтверждения.
  4. Не решено, может ли у одного автора быть несколько профилей стиля (1 → 1 или 1 → N).

4. Выбор базы данных

Основа — PostgreSQL с pgvector

PostgreSQL
+ pgvector

Почти все данные BlogOS структурированы и связаны внешними ключами: автор → черновик → отчёт, источник → комментарий → ответ. Для этого лучше всего подходит реляционная база.

Результаты AI (замечания AntiCringe) хранятся в JSONB, а векторы для RAG — через расширение pgvector. Поэтому на этапе MVP отдельная векторная база не нужна: всё лежит в одном месте.

Redis

Не основная база. Нужен для очередей, кэша и фоновых задач, например для проверки новых комментариев CommentRadar.

Объектное хранилище

Для файлов и аудиорасшифровок, если они появятся. В PostgreSQL лежат только их метаданные.

5. Как BlogOS работает с данными

Шесть действий

Автор подключается

Через Telegram создаётся запись в users, затем профиль канала в author_profiles и его стиль в tov_profiles.

Загружается архив

Старые посты попадают в posts, из них строятся embeddings. Так ИИ знает прошлые темы автора.

Появляется черновик

Автор или Narrative Engine создаёт запись в drafts. При каждой правке меняется текст, а не создаётся новый черновик.

AntiCringe проверяет

Каждая проверка добавляет строку в lint_reports с оценкой и замечаниями. Запуск модели пишется в generation_runs.

CommentRadar ищет

Новые комментарии из sources сохраняются в comments, а варианты ответов — в generated_responses.

Пост публикуется

Готовый текст уходит в posts и сразу получает свои embeddings, чтобы следующий пост учитывал его.
