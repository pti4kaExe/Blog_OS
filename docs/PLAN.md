# План разработки BlogOS

План собран с ИИ из описания проекта и анализа конкурентов (прошлая работа) и
ведётся по одному блоку за раз. Для каждого блока заранее формулируется
**ожидаемый результат** и **проверка основного сценария**; после блока сценарий
проверяется руками, а не «по ощущению», и только потом начинается следующий блок.

Журнал выполнения, промты и найденные ошибки — [`development_log.md`](../development_log.md).

---

## Принципы ведения плана

1. **Один блок — один проверяемый результат.** Блок не «готов», пока основной
   сценарий не проходит целиком.
2. **Ожидаемый результат формулируется до кода.** Иначе проверка превращается в
   «вроде работает».
3. **Сначала сценарий, потом расширение.** Сначала одна дорожка от входа до
   результата, затем глубина (AI, площадки, настройки).
4. **Каждое исправление закрывается тестом** или явной записью в журнале, если
   тестом закрыть нельзя (например, отключённый API площадки).
5. **Никаких декоративных функций.** Если настройка сохраняется, но ни на что не
   влияет — это ошибка, а не «задел на будущее».

## Блок 7. Правила AntiCringe (текущая итерация)

**Почему сейчас:** это последний пункт ТЗ из антикринж-ветки — «автор настраивает,
что для него неприемлемо», — и он же даёт самый понятный демонстрационный эффект:
правило видно в тексте и в отчёте.

| Что | Содержание |
|---|---|
| Ожидаемый результат | В настройках канала есть список своих запрещённых слов и оборотов: добавить, удалить, сохранить. При проверке черновика каждое совпадение — отдельное замечание с цитатой. Работает без AI, в локальном и облачном режиме одинаково |
| Что не входит | Автозамена, регулярные выражения, общие правила для всех каналов |
| Данные | Поле `stop_words` (профиль стиля). Схема не меняется: поле уже было в `tov_profiles`, но движок его не читал |
| API | `PUT /author-profiles/{id}/tov` (полная замена профиля) — новый метод не нужен |
| Движок | Правило `tov:stopword`, категория Tone of Voice, вес `med` |
| Проверка | Правило «синергия» → черновик «создаём синергию» → замечание с цитатой; удалить правило → после повторной проверки замечания нет |
| Тесты | 6 проверок движка (словоформа, оборот, границы слов, пустой список, без профиля) + 1 тест API «правила из профиля попадают в отчёт» |

Итог блока: реализовано, покрыто тестами, описано в
[`features/anticringe-rules.md`](features/anticringe-rules.md). По ходу блока
найдены две ошибки — журнал, записи «Ошибка 1» и «Ошибка 2».

## Блок 8. Реальные эмбеддинги (следующий)

- **Ожидаемый результат:** поиск по базе знаний находит факты по смыслу, а не по
  совпадению слов; в облаке используется настоящая модель эмбеддингов.
- **Проверка:** запрос «сколько стоит подписка» → находится факт «тариф 990 ₽
  в месяц», хотя слов «стоимость» в тексте нет.
- **Риск:** модель эмбеддингов платная → нужен лимит расходов и откат на
  лексический поиск при недоступности. Решение принимается до кода.

## Блок 9. «Сделать всё»

- **Ожидаемый результат:** одна кнопка проходит конвейер: стиль → черновик →
  проверка → отчёт, с прогрессом по шагам и возможностью отменить.
- **Проверка:** вставить заметки, нажать один раз, получить пост и отчёт; повторный
  запуск не дублирует черновики.

## Блок 10. Мобильная полировка

- **Ожидаемый результат:** на 390 px все четыре шага и CommentRadar пригодны:
  ничего не обрезано, кнопки доступны, таблицы не ломают вёрстку.
- **Проверка:** ручной проход по сценарию на телефоне.

## Блок 11. Защита

- **Ожидаемый результат:** видео 60–90 секунд по сценарию из
  [`DEMO-SCRIPT.md`](DEMO-SCRIPT.md) и 4 скриншота ключевых экранов.
