# Архитектура BlogOS 2.0

Документ объясняет, как устроена целевая версия и почему именно так.
Решения с обоснованием — в [DECISIONS.md](DECISIONS.md), контракт API — в [API.md](API.md).

## Три уровня

```
┌──────────────────────────────────────────────────────────────────────┐
│ Клиент (apps/web) — React 18 + Vite, один билд для двух режимов      │
│  Локальный режим: движки в браузере, состояние в localStorage        │
│  Облачный режим: тот же конвейер, но данные в API и PostgreSQL       │
└───────────────┬──────────────────────────────────────────────────────┘
                │ HTTP /api/v1 · JWT Bearer
┌───────────────▼──────────────────────────────────────────────────────┐
│ API (apps/api) — Fastify 5 + TypeScript, node: 59 методов            │
│  routes → repositories ↔ PostgreSQL · services → правила и LLM       │
│  Правиловый слой (@blogos/engine) работает всегда, LLM — второй      │
└───────────────┬──────────────────────────────────────────────────────┘
                │ SQL (pg / PGlite)                    │ HTTP (площадки, LLM)
        ┌───────▼─────────────────┐          ┌────────▼──────────────────┐
        │ PostgreSQL 16 + pgvector│          │ Telegram · Instagram ·    │
        │ 14 таблиц, 17 FK, HNSW  │          │ YouTube · LLM · эмбеддинги│
        └─────────────────────────┘          └───────────────────────────┘
```

## Почему движки — отдельный пакет

`packages/engine` — чистые функции без сети и DOM: `text`, `styleProfile`,
`narrative`, `anticringe`, `radar`, `rules`, `demoData`. Два потребителя:

- **клиент** — локальный режим: Шаги 1—4 считаются мгновенно, без сервера,
  без ключей; это и есть проверенная часть проекта из ТЗ (раздел 1);
- **сервер** — первый слой проверки и откат при отказе LLM. Интерфейс
  `lint(text, profile)` не меняется, поэтому нейросеть добавляется вторым
  источником замечаний, а не заменой движка (ТЗ, раздел 8).

Зависимости однонаправленные: `text → styleProfile → narrative / anticringe / radar`.
49 тестов движков — общий регрессионный барьер для обоих потребителей.

## Два драйвера базы под одним интерфейсом

`apps/api/src/db.ts` экспортирует `query`, `queryOne`, `transaction`, `exec`
и выбирает драйвер по `DATABASE_URL`:

| Строка | Драйвер | Когда |
|---|---|---|
| `postgresql://…` | `pg` (пул соединений) | Продакшен: Neon, Render, Docker |
| `pglite://memory` | PGlite (WASM) | Тесты: настоящий PostgreSQL, но в памяти |
| `pglite://.pglite-data` | PGlite + файл | Демонстрация и разработка без Docker |

PGlite — это PostgreSQL 16, скомпилированный в WASM, вместе с pgvector:
те же типы, ограничения, триггеры, `vector(1536)` и HNSW. Поэтому один и тот же
DDL и один и тот же SQL репозиториев работают везде, а проверяющему не нужен
ни Docker, ни аккаунт облачной базы. Ограничение: одно соединение — транзакции
сериализуются очередью, поэтому в PGlite-режиме нагрузка не параллельная.

## Слои сервера

```
src/routes/<группа>.ts      HTTP-обвязка: схемы zod, коды, монтирование
src/auth.ts                 проверка Telegram initData, JWT, requireUser/requireAdmin
src/repositories/<сущность> SQL и правила доступа: «своё» фильтруется в запросе
src/services/lint.ts        правила + второй слой LLM, пересчёт оценки
src/services/narrative.ts   сборка поста из заметок
src/services/tov.ts         анализ стиля, метрики карточки
src/services/llm/*          провайдеры mock / deepseek / openai, ретрай, таймаут
src/services/embeddings.ts  векторы текстов (mock / openai / none)
src/services/rag.ts         поиск по pgvector с косинусным расстоянием
src/services/cost.ts        прайс, расходы, лимит канала, блокировка
src/services/evals.ts       precision/recall по golden_dataset
src/adapters/*              Telegram, Instagram, YouTube: импорт и сканирование
src/lib/*                   пагинация, ошибки, форматирование
```

Правило: **проверка прав живёт в репозиториях**, а не в роутерах. Каждая
выборка фильтруется по владельцу, поэтому «забыть guard» в новом методе
сложнее. Чужая запись неотличима от несуществующей — 404, а не 403
(не раскрываем существование данных).

## Поток одной проверки текста

```
POST /drafts/{id}/lint
  │
  ├─ 1. загрузить черновик и профиль стиля канала (репозиторий, проверка владельца)
  ├─ 2. правила: lint(text, profile) из @blogos/engine → score, issues, группы
  ├─ 3. лимит расходов канала: если исчерпан — LLM пропускается
  ├─ 4. LLM-слой (если включён и доступен): смысловые и логические замечания
  │      ошибка → одна повторная попытка → откат на правила
  ├─ 5. INSERT lint_reports (неизменяемо) + generation_runs (журнал вызова)
  └─ 6. ответ: score, issues, verdict, engine, verified_without_ai
```

Ключевые инварианты:

- **Отчёт неизменяем.** Повторная проверка — новая запись; историю видно,
  подмены прошлого результата не бывает (триггер в базе).
- **Оценка всегда относится к текущему тексту.** Вердикт пересчитывается,
  «можно публиковать» не переносится на изменённый текст.
- **Никаких выдуманных фактов.** Narrative Engine не выдумывает, а черновик
  ответа оставляет `[дополните: …]`; публикация и одобрение с пропуском
  запрещены (422 `unfilled_gaps`).
- **Публикация не отправляет пост на площадку** — фиксирует факт и связывает
  черновик с архивом (границы проекта, ТЗ раздел 3).

## Отказы и деградация

| Что отказало | Что происходит | Что видит автор |
|---|---|---|
| LLM недоступна/таймаут | одна повторная попытка → правила | `verified_without_ai: true`, `engine: "rules"`, запись в журнале с ошибкой |
| Лимит расходов исчерпан | AI-вызов не выполняется | `402 ai_budget_exceeded` + работа на правилах, `warning` при 80% |
| Эмбеддинги недоступны | поиск по базе знаний недоступен | `503` только на `/knowledge/search`, остальное работает |
| Площадка недоступна | одна повторная попытка → пометка источника | `502` + `last_scan_status=failed`, старые комментарии на месте |
| Ключей площадки нет | адаптер не настроен | `503 not_configured`, остальные площадки работают |
| Telegram недоступен при входе | одна повторная попытка | `503`, открытая сессия продолжает работать |
| API недоступен целиком | клиент не падает | предложение локального режима, данные в localStorage |

## Безопасность

- Секреты (ключи LLM, площадок, `JWT_SECRET`) — только в переменных окружения
  сервера; в клиентский бандл не попадают.
- `DEV_AUTH=1` — только для локальной проверки; на проде `0`, иначе вход
  подделывается парой `telegram_id/name`.
- Тексты автора уходят внешнему провайдеру только при AI-вызове; перед первым
  вызовом клиент показывает предупреждение и позволяет отказаться (`use_llm: false`).
- Администратор работает со служебными данными (`golden_dataset`, Evals),
  а не с личными записями авторов.
- Ошибки наружу отдают код и безопасный текст; исключения — только в лог.

## Что осталось за границей архитектуры

Планировщик публикаций, аналитика вовлечённости, монетизация — вне проекта
(ТЗ, раздел 3). Настройка правил AntiCringe автором — интерфейс не описан,
реализована только часть со стоп-словами (DECISIONS, № 14). Согласие на
передачу текста хранится на клиенте, поля в схеме нет (DECISIONS, № 28).
