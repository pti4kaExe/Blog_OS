# BlogOS (ContentOS Guardian) — клиент

Клиент BlogOS: локальный прототип из четырёх шагов + CommentRadar и целевой
облачный режим поверх BlogOS API (docs/API.md).

## Быстрый старт

Нужен Node.js 20 или новее (проверить: `node -v`; скачать: https://nodejs.org).

```bash
npm install
npm run dev -w @blogos/web
```

Откроется на http://localhost:5173 — адрес появится в терминале.

Демо локального режима за 5 кликов: **«Взять демо-автора» → «Дальше: заметки» → «Пример заметок» → «Собрать пост» → «Проверить в AntiCringe»**.

## Два режима

Переключатель **«Локально / В облаке»** — в шапке. Выбор сохраняется в
`localStorage` (`blogos.mode.v1`).

| Режим | Что работает | Данные |
|---|---|---|
| **Локально** | 4 шага конвейера и CommentRadar на движках `@blogos/engine` | `localStorage`, ключ `blogos.state.v1`; сеть не нужна |
| **В облаке** | вход, каналы, профиль стиля, черновики, проверки с историей, публикация, CommentRadar с реальными источниками, база знаний с RAG, расходы | сервер BlogOS API; JWT в `localStorage` (`blogos.token.v1`) |

Если API недоступен, клиент не падает: показывает причину и предлагает
локальный режим, который продолжает работать без сети.

### Вход в облако

- Внутри Telegram вход автоматический: `window.Telegram.WebApp.initData` →
  `POST /auth/telegram`.
- Вне Telegram сервер запускается с `DEV_AUTH=1`, тогда на экране входа
  доступна dev-форма (`telegram_id`, имя).

### Настройка API

Скопируйте `apps/web/.env.example` в `apps/web/.env` (или `.env.local`) и
укажите адрес сервера:

```bash
VITE_API_URL=http://localhost:3000
```

Если переменная не задана, используется `http://localhost:3000`.

---

Рабочая стартовая версия проекта из описания: инструмент для авторов каналов и блогов,
который помогает **создавать контент в авторском стиле**, **находить обсуждения для ответов**
и **проверять черновик на клише, логические ошибки и отклонения от Tone of Voice**.

## Гипотеза, которую проверяет прототип

> Нужен ли авторам единый инструмент, который одновременно сохраняет их стиль,
> помогает собрать сюжет поста и проверяет готовый текст перед публикацией.

Из исследования ниши: у Buffer, Hootsuite, Jasper, Grammarly и Taplio функции разбросаны
по разным продуктам — кто-то силён в публикациях, кто-то в генерации, кто-то в редактуре.
Наличие AI само по себе уже не отличие. Отличие — **связка** личного стиля, контекста прошлых
публикаций, автоматической проверки качества и работы с внешними обсуждениями в одном процессе.
Прототип собран именно вокруг этой связки, а не вокруг отдельной функции.

## Главный сценарий (работает от начала до результата)

1. **Стиль.** Автор вставляет 2–3 своих поста → система строит профиль Tone of Voice:
   длина предложений, доля «я», обращение на «ты»/«вы», эмодзи, вопросы, канцелярит, темы.
2. **Заметки.** Автор бросает сырые мысли — по одной в строке. (Или вставляет готовый
   черновик и идёт сразу к проверке.)
3. **Пост.** Narrative Engine раскладывает заметки по ролям в истории, расставляет их
   по сюжетной арке и подгоняет ритм под профиль. Видно, из чего собран каждый блок
   и что именно добавил движок.
4. **Проверка.** AntiCringe даёт оценку 0–100, разбивку по четырём группам, список конкретных
   замечаний с цитатами и автоправки. Оценка пересчитывается сразу — прогресс «было → стало» виден.

Результат: готовый пост в своём голосе + отчёт о том, что в нём не так и почему.

Отдельная вкладка — **CommentRadar**: лента обсуждений, отсортированная по совпадению
с темами автора, и черновик комментария, собранный из его же прошлых постов.

## Что реализовано по-настоящему (не заглушки)

Всё считается локально в браузере, без внешних API и ключей.

| Модуль | Что делает |
|---|---|
| `engine/styleProfile.js` | Профиль Tone of Voice: 15+ метрик, темы автора, частые связки, стиль начала поста |
| `engine/narrative.js` | Разбор заметок на фрагменты, определение роли каждого (зацепка, конфликт, перелом, доказательство, вывод), 3 сюжетные арки, автовыбор арки по структурным признакам, деление длинных предложений под ритм автора |
| `engine/anticringe.js` | 4 группы проверок: клише, логика, Tone of Voice, ясность. Поиск противоречий между предложениями, категоричности, цифр без источника, логических скачков, канцелярита, воды. Автоправки с расширением до оборота или предложения |
| `engine/rules.js` | ~90 правил: словари инфобизнес-клише, канцелярита, обещаний, кванторов |
| `engine/radar.js` | Ранжирование обсуждений по темам автора с объяснением совпадения + поиск подходящего фрагмента из прошлых постов автора для основы комментария |

Принципы, заложенные в движок:

- **Слова автора не переписываются.** Narrative Engine меняет порядок и ритм, но не формулировки.
- **Движок не выдумывает факты.** В черновике комментария остаётся явный пропуск `[дополните: …]`,
  который заполняет человек. Кнопка «Одобрить» заблокирована, пока пропуск на месте.
- **Автоправка не должна ломать грамматику.** Например, замена «вы» → «ты» в именительном падеже
  не применяется автоматически: изменилась бы форма глагола.

## Команды

```bash
npm run dev          # запуск в режиме разработки
npm run build        # production-сборка в папку dist
npm run preview      # просмотр собранной версии
npm run test:engine  # проверки движков (49 тестов, без браузера)
```

Если порт 5173 занят: `npm run dev -- --port 5175`.

## Стек

React 18 + Vite. Без UI-библиотек, стейт-менеджеров и бэкенда: состояние — `useState`,
сохранение — `localStorage`. Логика движков вынесена в чистые функции в `src/engine/`,
поэтому её можно тестировать и заменять независимо от интерфейса.

## Данные

- Тексты автора остаются в браузере (`localStorage`), никуда не отправляются.
- Лента CommentRadar — **демонстрационные данные** (`src/engine/demoData.js`). Обсуждения
  и авторы вымышлены, это не выгрузка реальных площадок. В интерфейсе помечено бейджем.

## Сознательно вне MVP

Не нужны для проверки основной гипотезы: авторизация и аккаунты, бэкенд и база данных,
оплата, реальные интеграции с соцсетями, публикация и планировщик, аналитика охватов,
командные роли, история версий, мультиязычность. Движок AntiCringe правиловый — под реальный
продукт его место заняли бы LLM + RAG по прошлым постам + evals, о которых идёт речь
в описании проекта; для прототипа важнее, что проверка работает и её результат можно оценить.
